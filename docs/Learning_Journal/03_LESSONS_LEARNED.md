# Lessons Learned — Challenges Faced & How They Were Solved

Every real problem hit while building this pipeline, in roughly the order encountered. Kept deliberately blunt — the point of this doc is to save future-me from re-learning the same lesson the hard way.

| # | Challenge | Root cause | How it was fixed | Lesson for next time |
|---|-----------|-----------|-------------------|----------------------|
| 1 | Shell commands failing / behaving inconsistently while setting up locally on Windows | Mixed guidance (and habit) between `cmd.exe`, PowerShell, and Git Bash — each has different syntax for redirection, path separators, and copy/env commands | Standardized on one shell per task and translated commands explicitly (e.g. `cp` → `Copy-Item`, `$VAR` vs `%VAR%` vs `$env:VAR`) instead of assuming Unix syntax "just works" on Windows | On Windows, decide up front which shell you're in before pasting any command from a tutorial — most CI/CD tutorials assume a Unix shell and will silently fail or do the wrong thing under `cmd.exe` |
| 2 | Git commands not recognized / wrong Git found | Git wasn't on the expected `PATH`, or an older bundled Git (e.g. from another IDE) was being picked up ahead of the intended install | Located the actual Git install path and corrected `PATH`/terminal configuration so the right Git binary ran | When a tool "isn't found" or behaves oddly on Windows, check `where <tool>` first — multiple installs shadowing each other is a very common cause |
| 3 | EC2 networking didn't behave like tutorials assumed (no obvious default VPC/subnet) | This AWS account is managed under **AWS Organizations / Control Tower**, not a bare personal account — Control Tower's account vending often does *not* leave the classic flat "default VPC" that most solo-account tutorials assume, and may apply region or networking guardrails | Worked with the account's actual VPC/subnet/route-table layout as it existed, rather than assuming a default VPC, and picked a region actually permitted for the resources being created | Never assume "default VPC exists" in a managed/organization AWS account — check the actual VPC console first. Org-managed accounts can also have Service Control Policies restricting regions or resource types |
| 4 | Files ended up in the wrong folder / project structure got confusing mid-build | Two near-identical folders existed (`flask_Practice` scaffold vs `flask_Practice_repo` the actual git repo) and edits were sometimes made in the wrong one | Standardized on `flask_Practice_repo` as the single source of truth being pushed to GitHub, and mirrored any needed fix into the scaffold copy when relevant | When a project has a "working copy" and a "repo copy," rename one of them to make the distinction impossible to miss, or delete the redundant one entirely once it's no longer needed |
| 5 | `SECRET_KEY` misconfigured in the environment | Pasted the *command* used to generate a secret key (e.g. a Python one-liner) into the environment variable slot, instead of pasting the *output value* of that command | Ran the key-generation command separately, copied only the resulting string, and set that as the `SECRET_KEY` value | Always double-check whether a setup instruction wants you to *run* a command or *paste its output* — these look similar in a guide but are very different mistakes |
| 6 | `git push` rejected — histories diverged | The GitHub repo had commits (from the original template/fork) that weren't in the local history, so a normal push was rejected as a non-fast-forward | Diagnosed with `git log --oneline A..B` and `git show <sha>` to confirm which commits were "theirs" (template scaffolding, safe to overwrite) vs "mine," then used `git push --force-with-lease` to intentionally overwrite the stale template history with the real project history | `--force-with-lease` (not bare `--force`) is the safer choice when you're confident you should win a diverged push — it still fails safely if someone else pushed in between your fetch and your push |
| 7 | Mid-project pivot in which repo was "the" repo | Started work assuming one repo path, then needed to consolidate onto the actual repo intended for submission | Migrated all in-progress work over to the correct repo before continuing, rather than trying to keep both in sync | Settle on the exact repo (and confirm the remote URL) *before* doing significant work — a mid-flight pivot costs real time reconciling two histories |
| 8 | Docker image builds were slower/bulkier than expected, and early images risked including files that shouldn't ship | No `.dockerignore` existed yet, so `docker build`'s context included git metadata, docs, virtualenvs, etc. | Added a `.dockerignore` excluding `.git`, `.github`, `venv/`, `__pycache__`, docs, and secret-bearing files | Add `.dockerignore` at the very start of containerizing a project, not as an afterthought — it affects both build speed and what could accidentally end up baked into a shipped image |
| 9 | App crashed connecting to MongoDB in one environment but not another | `PyMongo` was configured to force `tlsCAFile=certifi.where()` on *every* connection, but the CI test stage uses a plain non-TLS `mongodb://` service container, while production uses TLS-required Atlas (`mongodb+srv://`) — forcing TLS onto a non-TLS server causes a handshake failure | Made the `tlsCAFile` kwarg conditional on the URI starting with `mongodb+srv://`, so TLS is only forced for Atlas connections (see [`01_PROJECT_JOURNAL.md`](./01_PROJECT_JOURNAL.md) §3.2) | When the same code must run against two different environments (ephemeral test DB vs real managed DB), don't hardcode assumptions that only hold for one of them — branch on something observable (the URI scheme) instead |
| 10 | An unrelated workflow (a "SecureGate"-style check unrelated to this assignment) was interfering with pipeline runs/status | A leftover or unrelated GitHub Actions workflow file was present in the repo and triggering alongside the intended CI/CD pipeline, muddying which run/status actually mattered | Identified the extra workflow and removed/disabled it so only the intended `ci-cd.yml` pipeline runs and reports status | Before trusting a repo's Actions tab, check *all* workflow files under `.github/workflows/` — it's easy to inherit stray workflows from a template or an earlier experiment |
| 11 | Deploy stage timed out trying to reach EC2 over SSH (port 22) | The instance's security group didn't allow inbound port 22 from the GitHub Actions runner's IP (runner IPs are dynamic and not knowable in advance), or the instance wasn't fully booted/reachable yet | Adjusted the security group's inbound rule for port 22 appropriately for CI access, and confirmed the instance was running and its public IP was current before retrying | GitHub-hosted runners don't have static IPs — if you need to lock SSH down tightly, you either need self-hosted runners with a known IP, or accept a broader (but still key-authenticated) inbound rule for automated deploys |
| 12 | App failed to connect to MongoDB in production despite correct-looking config | `MONGO_URI` on the EC2 instance was still set to a placeholder/example value rather than the real Atlas connection string with actual credentials and cluster host | Replaced the placeholder with the real, correctly-formed `mongodb+srv://` URI (user, password, cluster address, db name) as an environment variable available to the running container | Placeholder values in `.env.example` or setup docs are easy to copy verbatim by habit — always diff a real config against the placeholder before trusting a "should be working" deploy |
| 13 | Two stale/competing files were sitting in the repo unnoticed | `azure-pipelines.yml` (a leftover pipeline definition from the original template, never actually used) and `README.pdf` (a stale duplicate of `README.md`) were both still present when reviewing the repo for submission | Removed both via `git rm` so the submitted repo shows exactly one pipeline definition (`.github/workflows/ci-cd.yml`) and one canonical README | Do a full top-level `git ls-files` pass before final submission — templates and forks often carry dead files forward that quietly confuse a reviewer about what's actually "the" pipeline |
| 14 | Risk of committing real credentials while reorganizing the repo for submission | Screenshots taken throughout the project (for evidence/documentation) include several that show real AWS access keys, the EC2 `.pem` private key, account IDs, and IPs in a sensitive context — and one screenshot (`Screenshot 2026-08-16 180948.png`) shows a live AWS `AccessKeyId`/`SecretAccessKey` pair in plaintext | Manually reviewed every screenshot, sorted them into `docs/Screenshots_Safe/` (trackable) vs `PRIVATE_do_not_share/screenshots/` (gitignored), moved all secret material (`.pem` files, password notes) into the same gitignored folder, then **verified** the ignore rule actually works with three independent checks (`git status --ignored`, `git status --short`, `git add -A --dry-run`) before staging anything | `.gitignore` prevents *future* tracking but does nothing to un-expose a credential that was ever visible on screen. The correct response to "a real secret appeared in a screenshot" is to treat that credential as compromised and **rotate it in IAM**, regardless of where the screenshot file ends up living. This was flagged as an explicit action item — see the note at the bottom of `01_PROJECT_JOURNAL.md` |

## Gap worth noting

The pipeline's failure-path (Stage 8b, the failure email) was proven by **organic** failures encountered during development (real bugs listed above triggering real failed runs), not by a deliberately-injected test failure. If the assignment's grading rubric specifically wants a screenshot of an *intentionally broken* run plus its failure email, that's a 10-minute exercise (e.g. temporarily break a test assertion, push, capture the failed Actions run and the resulting email, then revert) that hadn't been performed as of this writing — worth doing before final submission if the rubric calls for it explicitly.
